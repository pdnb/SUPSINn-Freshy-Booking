## 1. Introduction

### 1.1 Purpose

กำหนดข้อกำหนดเชิงฟังก์ชันและนอกฟังก์ชันของระบบจองชุดเฟรชชี่สำหรับนักศึกษา มรส. ให้ทีมพัฒนาและผู้เกี่ยวข้องใช้เป็นต้นทางออกแบบ implement และทดสอบ โดยตัดขอบเขต **v1** กับ **Phase 2** ให้ชัด

### 1.2 Scope

ระบบเป็นเว็บแอปพลิเคชันแนว eCommerce (mobile-first) สำหรับ:

- **นักศึกษา:** ดูสินค้าในรอบที่เปิดจอง ใส่ตะกร้า กรอกข้อมูล จ่าย PromptPay แนบสลิป (ต้องผ่าน checksum) ติดตามออเดอร์ด้วยรหัส/ลิงก์ โดยไม่มีบัญชีล็อกอิน
- **เจ้าหน้าที่ (แอดมิน):** ล็อกอินจัดการสินค้าเต็มรูปแบบ สร้างรอบเปิดจองที่ผูกสินค้า ตั้งค่าส่ง ตรวจสลิป/ยืนยันชำระ จัดการสถานะออเดอร์

**ชื่อระบบ (ทำงาน):** Freshy Booking / ระบบจองชุดเฟรชชี่ มรส.

### 1.3 Definitions

| คำศัพท์ | ความหมาย |
| --- | --- |
| คอมโบเซ็ตปี 70 | ชุดบังคับซื้อทั้งชุด 4 รายการ (ไม่แยกชิ้น) ตาม FR-CAT-01 |
| ชุดเฟรชชี่ปี 69 | สินค้าซื้อแยกได้ (เสื้อ+กางเกง) ตาม FR-CAT-02 |
| รอบเปิดจอง | ช่วงเวลาเปิด–ปิดรับออเดอร์ที่ผูกกับชุดสินค้าที่เปิดขายในรอบนั้น |
| Checksum สลิป | การตรวจสอบเบื้องต้นจากข้อมูลใน QR บนสลิปโอน (ยอด/ความถูกต้อง/ไม่ซ้ำ ตามความสามารถของตัวตรวจ) |

## 2. Overall description

### 2.1 Product perspective

ระบบยืนบนโดเมน eCommerce มาตรฐาน (Product / Catalog / Cart / Checkout / Order / Payment / Admin) เพื่อรองรับแคมเปญเฟรชชี่ปัจจุบันและขยายสินค้า/รอบจองในอนาคต โดย v1 โฟกัสผู้ขายเดียว (ศูนย์หนังสือฯ) ไม่ใช่ multi-vendor marketplace

กฎธุรกิจอยู่ใน **application services** (`app/Services`) — Livewire เป็น UI เท่านั้น รายละเอียดกติกาดู `docs/decisions/ADR-002-application-services.md`

```text
[นักศึกษา - Livewire]              [เจ้าหน้าที่ - Livewire]
        |                                  |
        v                                  v
              Application Services
     Catalog · Booking · Shipping · Cart
     Checkout · Order · Payment/Slip
        |                                  |
        +-------- Persistence (Eloquent) --+
        |
        +-- SlipVerifier (contract) --> adapter / บริการภายนอก
```

### 2.2 User classes

| ผู้ใช้ | คำอธิบาย | ล็อกอิน |
| --- | --- | --- |
| นักศึกษา / ผู้จอง | สั่งซื้อชุดเฟรชชี่ ชำระเงิน ติดตามสถานะ เลือกรับของหรือจัดส่ง | ไม่มี |
| เจ้าหน้าที่ | จัดการแค็ตตาล็อก รอบจอง ค่าส่ง ตรวจสลิป อัปเดตสถานะออเดอร์ | มี |

### 2.3 Operating environment

- เบราว์เซอร์สมัยใหม่บนมือถือเป็นหลัก (mobile-first) และเดสก์ท็อปใช้งานได้
- แอดมินใช้งานบนเดสก์ท็อป/แท็บเล็ตได้สะดวก
- ภาษา UI หลัก: ภาษาไทย
- ดูแนวภาพจาก mockup: โทนน้ำเงิน–เทา–ขาว, ฟอนต์ Anuphan (ดู brand-spec)

### 2.4 Design / implementation constraints

- สถาปัตยกรรมและโมเดลข้อมูลต้องเป็นแนว eCommerce (สินค้า ตัวเลือก/ไซส์ ตะกร้า ออเดอร์ การชำระเงิน) ไม่ผูก hardcode เฉพาะแคมเปญเดียวในชั้นโดเมน
- กฎธุรกิจ (รอบเปิด, คอมโบ, ค่าส่ง, เกตสลิป, สถานะออเดอร์) อยู่ใน application services ไม่ใช่ใน Livewire/Blade (ADR-002)
- การชำระเงิน v1: PromptPay สแกน QR + แนบสลิปเท่านั้น
- สต็อก: **ไม่** กันของตอนจอง — รับออเดอร์ได้เรื่อยๆ
- ใบเสร็จ: ออกตอนรับสินค้า (ไม่บังคับออกอิเล็กทรอนิกส์ตอนจองใน v1 เว้นแต่ทีมเลือกเพิ่มภายหลัง)

### 2.5 Assumptions and dependencies

**ASSUMPTIONS (แก้ได้ทันทีถ้าผิด):**

1. เป็น **เว็บแอป** responsive ไม่ใช่แอป native
2. ผู้ให้บริการ/ร้านเดียว (ศูนย์หนังสือฯ) — ไม่มี marketplace หลายร้านใน v1
3. QR PromptPay และยอดที่ต้องโอนมาจากระบบตามยอดออเดอร์ (สินค้า + ค่าส่งถ้ามี)
4. มีบริการหรือไลบรารีตรวจ **checksum/QR สลิป** ใช้ได้ในสภาพแวดล้อม deploy จริง
5. แอดมินล็อกอินด้วยบัญชีที่ระบบจัดการเอง (เช่น อีเมล/รหัสผ่าน) — ยังไม่ผูก SSO มหาวิทยาลัยใน v1
6. รอบเปิดจองหลายรอบมีในระบบได้ แต่หน้าร้านแสดงเฉพาะสินค้าจากรอบที่ **กำลังเปิด** ตามเวลาปัจจุบัน
7. นักศึกษาสั่งได้หลายออเดอร์ (ไม่จำกัด 1 คน / 1 ออเดอร์) เพราะไม่ล็อกอินและไม่ล็อกสต็อก
8. Tech stack ล็อกแล้ว: **Laravel + Livewire + SQLite/MySQL/PostgreSQL + Redis** (ดู `tasks/plan.md`)
9. Application services ล็อกแล้ว: กฎธุรกิจอยู่ใน `app/Services`; พอร์ตภายนอกอยู่ใน `app/Contracts` (ดู ADR-002)

**Dependencies:** บริการธนาคาร/PromptPay, ตัวตรวจสลิปจาก QR, ที่เก็บไฟล์สลิป, โฮสติ้งเว็บ

## 3. System features (Functional requirements)

รหัส: `FR-<AREA>-<nn>`  
ลำดับความสำคัญ: **P0** = ต้องมีใน v1, **P1** = ควรมีใน v1, **P2** = Phase 2

### 3.1 Catalog & product types

#### FR-CAT-01 คอมโบเซ็ตปี 70 (ชุดรวม) — P0

ระบบต้องรองรับสินค้าประเภท “บังคับทั้งชุด” ประกอบด้วยอย่างน้อย:

1. ชุดนักศึกษา: (เสื้อ ชาย|หญิง) + (กางเกง|กระโปรง) ระบุไซส์ได้
2. ชุดเฟรชชี่: เสื้อ + กางเกง ระบุไซส์ได้
3. เสื้อกิจกรรม: ระบุไซส์ได้
4. เครื่องหมาย: ระบุไซส์เข็มขัดได้

**Acceptance**

- ผู้จองไม่สามารถซื้อรายการย่อยของคอมโบแยกชิ้นได้
- ต้องเลือกตัวเลือก/ไซส์ครบทุกส่วนประกอบก่อนใส่ตะกร้าหรือ checkout
- ราคาที่คิดเป็นราคาชุดตามที่กำหนดในสินค้า

#### FR-CAT-02 ชุดเฟรชชี่ปี 69 (ซื้อแยกได้) — P0

- ซื้อเสื้อและ/หรือกางเกงแยกได้
- ระบุไซส์ได้ต่อรายการ

#### FR-CAT-03 หลังบ้านจัดการสินค้าเต็มรูปแบบ — P0

แอดมินต้องสามารถอย่างน้อย:

- สร้าง / แก้ไข / ปิดหรือเปิดการขายสินค้า
- กำหนดราคา
- กำหนดประเภทสินค้า (เช่น combo bundle vs ซื้อแยก)
- กำหนดตัวเลือก (เพศแบบเสื้อ, กางเกง/กระโปรง, ไซส์, ไซส์เข็มขัด ฯลฯ)
- อัปโหลดหรือจัดการรูปประกอบสินค้า (อย่างน้อย 1 รูปต่อสินค้า หรือตามที่ออกแบบ UI)

**หมายเหตุ:** รายการปี 69/70 ใน `features.md` เป็นตัวอย่างแคมเปญตั้งต้น ไม่ได้จำกัดว่าโดเมนสินค้ามีได้แค่สองรายการ

### 3.2 Booking rounds (รอบเปิดจอง)

#### FR-RND-01 สร้างและจัดการรอบ — P0

แอดมินสร้างรอบเปิดจองได้ โดยแต่ละรอบมีอย่างน้อย:

- ชื่อรอบ
- เวลาเริ่มเปิดจอง
- เวลาปิดจอง
- สถานะ (เช่น draft / scheduled / open / closed) ที่สอดคล้องกับเวลา หรือควบคุมด้วยการเปิด–ปิดด้วยมือร่วมกับหน้าต่างเวลา (รายละเอียดพฤติกรรมให้ล็อกตอนออกแบบ — ดู Open Questions)

#### FR-RND-02 ผูกสินค้าในรอบ — P0

- แต่ละรอบระบุได้ว่าสินค้าใดอยู่ในรอบนั้น
- หน้าร้านแสดงเฉพาะสินค้าที่อยู่ในรอบที่เปิดรับจองอยู่
- สินค้าที่ไม่อยู่ในรอบเปิดต้องไม่สามารถ checkout ได้

#### FR-RND-03 พฤติกรรมนอกช่วงเปิดจอง — P0

- นอกช่วงรอบเปิด: หน้าร้านสื่อสารชัดว่ายังไม่เปิดจอง / ปิดจองแล้ว
- ไม่รับสร้างออเดอร์ใหม่เมื่อไม่มีรอบเปิดที่ครอบคลุมสินค้าในตะกร้า

### 3.3 Cart & checkout (นักศึกษา)

#### FR-CHK-01 ตะกร้า — P0

- เพิ่ม/แก้จำนวน/ลบสินค้า (ภายใต้กฎ combo)
- คงตัวเลือกไซส์ที่เลือกไว้จน checkout

#### FR-CHK-02 ข้อมูลผู้จอง — P0

บังคับกรอกอย่างน้อย:

- รหัสนักศึกษา
- ชื่อ–นามสกุล
- คณะ
- เบอร์โทรศัพท์

#### FR-CHK-03 ช่องทางรับสินค้า / จัดส่ง — P0

ผู้จองเลือกได้อย่างน้อยหนึ่งแบบต่อออเดอร์:

1. รับที่ร้านศูนย์หนังสือฯ  
2. รับที่หอประชุมฯ วันรายงานตัว  
3. จัดส่งทางไปรษณีย์ (คิดค่าส่งเพิ่ม)

#### FR-CHK-04 ค่าจัดส่งตามช่วงจำนวน — P0

- แอดมินตั้งเรทค่าส่งได้ (อย่างน้อย 1–2 เรท) และกำหนดช่วงจำนวนต่อเรท เช่น 1 ชิ้น = 50, 2–3 ชิ้น = 80, 4+ ชิ้น = 120
- นับชิ้นจากผลรวม qty ทุกบรรทัดในตะกร้า; จำนวนที่เกินช่วงที่ใช้ได้ใช้ยอดของช่วงสูงสุดที่มี
- ตอน checkout แสดงค่าส่งและยอดรวมก่อนชำระ (ลูกค้าไม่เลือกเรท — ใช้เรท active แรกตามลำดับ)
- ยอด PromptPay = ยอดสินค้า + ค่าส่ง (ถ้าเลือกจัดส่ง)

#### FR-CHK-05 ไม่มีล็อกอินนักศึกษา — P0

- จองได้โดยไม่สมัครสมาชิก
- หลังสั่งสำเร็จได้รหัสออเดอร์และ/หรือลิงก์ติดตามสถานะ

### 3.4 Payment & slip

#### FR-PAY-01 PromptPay + แนบสลิป — P0

- แสดง QR PromptPay และยอดที่ต้องชำระ
- ผู้จองอัปโหลดสลิปเป็นส่วนหนึ่งของขั้นตอนจบการจอง

#### FR-PAY-02 Checksum จาก QR สลิป (เกตบังคับ) — P0

ก่อนรับออเดอร์เป็นผลสำเร็จ ระบบต้องรันการตรวจเบื้องต้นจาก QR บนสลิปอย่างน้อยในมิติ:

- อ่าน QR ได้
- ยอดตรงกับยอดออเดอร์ (ตามความสามารถของตัวตรวจ)
- ไม่เป็นสลิปซ้ำกับออเดอร์อื่นในระบบ (ตามความสามารถของตัวตรวจ)

**ถ้าไม่ผ่าน:** บล็อกไม่ให้จบการจอง — ต้องแนบสลิปใหม่ที่ผ่านก่อน  
**ถ้าผ่าน:** รับออเดอร์เข้าสถานะรอเจ้าหน้าที่ตรวจ/ยืนยัน (ไม่ถือว่า “ชำระแล้ว” จนกว่าเจ้าหน้าที่จะยืนยัน เว้นแต่ทีมนิยามสถานะย่อย — ดู FR-ORD-01)

#### FR-PAY-03 คิวตรวจโดยเจ้าหน้าที่ — P0

- ออเดอร์ที่ checksum ผ่านเข้าคิวให้เจ้าหน้าที่ตรวจสลิปและยืนยันหรือปฏิเสธได้
- การยืนยันของเจ้าหน้าที่เป็นเงื่อนไขก่อนสถานะพร้อมจัดส่ง/พร้อมรับของ

### 3.5 Orders & fulfillment

#### FR-ORD-01 สถานะออเดอร์ (ขั้นต่ำ) — P0

ระบบต้องรองรับสถานะที่แยกได้อย่างน้อย:

| สถานะ | ความหมาย |
| --- | --- |
| `awaiting_payment` | (ถ้ามีขั้นตอนแยกก่อนแนบสลิป) รอชำระ/รอสลิป |
| `pending_review` | แนบสลิปแล้ว checksum ผ่าน รอเจ้าหน้าที่ |
| `paid` / `confirmed` | เจ้าหน้าที่ยืนยันแล้ว |
| `rejected` / `need_reslip` | สลิปไม่ผ่านการตรวจโดยคน |
| `ready_for_pickup` | พร้อมรับที่จุดรับที่เลือก |
| `shipped` | ส่งไปรษณีย์แล้ว (ถ้ามี) |
| `completed` | รับของแล้ว / จบ |
| `cancelled` | ยกเลิก |

ชื่อสถานะใน UI เป็นภาษาไทยได้ แต่ต้อง map ได้ชัดในระบบ

#### FR-ORD-02 ติดตามออเดอร์แบบ guest — P0

- ดูสถานะด้วยรหัสออเดอร์และ/หรือลิงก์ลับ
- ไม่ต้องล็อกอิน

#### FR-ORD-03 ไม่ล็อกสต็อก — P0

- การสร้างออเดอร์ไม่ลดหรือกันสต็อกแบบ realtime

## 6. Data requirements (เชิงแนวคิด)

เอนทิตีหลัก (ไม่ผูก schema จริงจนกว่าจะเลือก stack):

- **Product** — ชื่อ, ราคา, ประเภท (bundle/simple), สถานะขาย, สื่อ
- **ProductOption / Variant** — ไซส์, เพศเสื้อ, กางเกง/กระโปรง, ไซส์เข็มขัด ฯลฯ
- **BundleComposition** — ส่วนประกอบบังคับของคอมโบ
- **BookingRound** — ช่วงเวลา, สถานะ
- **BookingRoundProduct** — ผูกสินค้าในรอบ
- **ShippingRate** — เรทพร้อมช่วงจำนวน (tiers)
- **Order** — ข้อมูลผู้จอง, ช่องทางรับของ, ที่อยู่จัดส่ง (ถ้ามี), ยอด, สถานะ, รอบจองอ้างอิง
- **OrderItem** — สินค้า/ตัวเลือกที่เลือก, ราคา ณ เวลาสั่ง
- **PaymentSlip** — ไฟล์, ผล checksum, เวลาอัปโหลด, ผลตรวจโดยคน
- **AdminUser** — บัญชีเจ้าหน้าที่

## 7. Boundaries

### Always

- บังคับ checksum ผ่านก่อนรับออเดอร์เข้าคิว
- แสดงและคิดค่าส่งตามเรทที่ตั้งไว้เมื่อเลือกไปรษณีย์
- หน้าร้านขายได้เฉพาะสินค้าในรอบที่เปิด
- แยกสถานะ “checksum ผ่าน” กับ “เจ้าหน้าที่ยืนยันแล้ว”
- กฎธุรกิจอยู่ใน application services ตาม ADR-002
- อัปเดตเอกสารนี้เมื่อเปลี่ยน scope หรือกฎธุรกิจ

### Ask first

- เลือก tech stack, hosting, ผู้ให้บริการตรวจสลิป
- เปลี่ยนกฎคอมโบหรือเพิ่มประเภทสินค้าพิเศษนอก bundle/simple
- เปิดล็อกอินนักศึกษาหรือผูกระบบมหาวิทยาลัย
- เปิดการล็อกสต็อก realtime
- ขอบเขตใบเสร็จภาษี / เลขประจำตัวผู้เสียภาษี
- เริ่ม implement FR-PCK-01 (Phase 2)
- แยก service เป็น Action ทีละคลาส หรือเพิ่ม repository ทับ Eloquent

### Never (v1)

- รับออเดอร์จบโดยสลิป checksum ไม่ผ่าน
- ให้นักศึกษาสมัคร/ล็อกอินเป็นเงื่อนไขจอง
- กันสต็อกอัตโนมัติแล้วปฏิเสธออเดอร์เพราะของหมด (ไม่ใช่พฤติกรรม v1)
- แทนที่การยืนยันของเจ้าหน้าที่ด้วยการผ่าน checksum อย่างเดียวแล้วถือว่าจ่ายเสร็จพร้อมมอบของ
- Scope ใส่ pickup assist เป็นเกณฑ์รับมอบ v1
- ใส่กฎรอบเปิด / คอมโบ / ค่าส่ง / เกตสลิป / transition สถานะใน Livewire หรือ Blade

## 8. Success criteria (รับมอบ v1)

v1 ถือว่าผ่านเมื่อทดสอบยืนยันได้ว่า:

1. แอดมินสร้างสินค้าแบบคอมโบปี 70 และแบบปี 69 (หรือเทียบเท่า) พร้อมตัวเลือกไซส์ได้จากหลังบ้าน  
2. แอดมินสร้างรอบเปิดจอง กำหนดช่วงเวลา และผูกสินค้าได้ — นอกช่วงเปิดแล้วสั่งไม่ได้  
3. นักศึกษา mobile จองสินค้าในรอบเปิด กรอกข้อมูล เลือกจุดรับหรือจัดส่ง เห็นค่าส่งตามช่วงจำนวน และยอดรวมถูกต้อง  
4. ไม่มีล็อกอินนักศึกษา; ได้รหัส/ลิงก์ติดตามหลังสั่ง  
5. ไม่แนบสลิปที่ checksum ผ่านแล้วจบออเดอร์ไม่ได้; สลิปไม่ผ่านถูกบล็อก  
6. ออเดอร์ที่ผ่าน checksum โผล่ในคิวแอดมิน; แอดมินยืนยัน/ปฏิเสธและเปลี่ยนสถานะจนถึงรับของหรือจัดส่งได้  
7. การจองไม่ล็อกสต็อก (สั่งซ้ำ/สั่งทับจำนวนได้ในระบบ)  
8. แอดมินตั้งเรทค่าส่งได้ และมีอย่างน้อยสองช่องทางรับของหน้าร้านตามที่ระบุ  

Phase 2 (ไม่บล็อกรับมอบ v1): มีการออกแบบ/implement pickup assist ตาม FR-PCK-01

## 10. Open questions

1. **ผู้ให้บริการตรวจสลิป QR** — ตัวเลือกและข้อจำกัด (ยอด, ชื่อบัญชี, กันซ้ำ)  
2. **PromptPay** — QR คงที่ของร้าน หรือสร้าง dynamic ตามยอดทุกออเดอร์  
3. **รอบจองซ้อนเวลา** — อนุญาตหลายรอบเปิดพร้อมกันหรือได้ทีละรอบ  
4. **ใบเสร็จ** — ใบเสร็จอย่างย่อในระบบพอ หรือต้องรูปแบบภาษี  
5. **ที่อยู่จัดส่ง** — ฟิลด์ที่อยู่เต็มรูปแบบที่ต้องบังคับเมื่อเลือกไปรษณีย์  
6. **การแจ้งเตือน** — มี SMS/อีเมล/LINE ตอนเปลี่ยนสถานะหรือไม่ (ไม่ถูกยืนยันใน grilling)  
7. **สิทธิ์แอดมิน** — บทบาทเดียวหรือแยก cashier / catalog manager  

**ปิดแล้ว:** Tech stack = Laravel + Livewire + SQLite/MySQL/PostgreSQL + Redis; application services ตาม ADR-002
